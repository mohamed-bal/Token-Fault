# Threat Model

- **Scope:** TokenFault 0.1.0, unreleased (proxy, mock, CLI, Studio, recordings).
- **Method:** asset- and entry-point-driven review. Each mitigation links to the code or test that implements it.
- **Status:** internal review only: one adversarial code review in phase 1 (T19, T20) and the phase 2 security and portability audit (T21–T26, `PHASE2_AUDIT.md`). Findings are fixed with regression tests. No external audit has been performed.

## 1. Assets

| Asset                                                        | Sensitivity                                 |
| ------------------------------------------------------------ | ------------------------------------------- |
| Upstream API keys (`Authorization`, `x-api-key`, query keys) | High: direct financial and account impact   |
| Prompts (request bodies)                                     | High: may contain personal or business data |
| Completions (response payloads)                              | Medium–High                                 |
| Upstream quota / billing                                     | Medium                                      |
| The developer's machine and local network                    | High                                        |

## 2. Trust boundaries and entry points

| Entry point                               | Who can reach it by default                                                    |
| ----------------------------------------- | ------------------------------------------------------------------------------ |
| Proxy data path (`/*`)                    | Processes on the same machine (loopback bind)                                  |
| Control API + Studio (`/__tokenfault/*`)  | Loopback peers with a loopback `Host` header **and** the control token (D-021) |
| Upstream responses                        | The configured upstream (untrusted content)                                    |
| Recording files (`replay`, Studio import) | Anyone who can give the developer a file (untrusted)                           |
| Web pages in the developer's browser      | Can send requests to `127.0.0.1` (CSRF, DNS rebinding)                         |
| CLI arguments and environment             | The local user                                                                 |

| T3  | **Network exposure**: bound to `0.0.0.0` by mistake                                                                                                                  | Loopback default. ## 4. Residual risks (accepted or open)

1. **Local multi-user machines.** The control API now requires the token (T25), but the **data path** stays open to
   every local process: anyone on the machine can send requests through the proxy to the configured upstream
   (they must supply their own credentials). The token is printed to the terminal that started the proxy, so
   terminal scrollback and screen sharing expose it. Other local users who can read the proxy process's
   environment (same user, or root) can read `TOKENFAULT_CONTROL_TOKEN`.
2. **`--allow-remote`** exposes the data path (not the control plane) to the network. Anyone who can reach the port
   can send requests through it to the configured upstream. The proxy never injects credentials, so they must
   supply their own, but they consume upstream capacity through it. This option is meant for trusted networks only.
3. **DNS rebinding against the mock server.** The mock has no Host check. It holds no secrets and only produces
   synthetic data.
4. **Mock-only scenario delegation** forwards `x-tokenfault-scenario` to the upstream. A third-party provider
   would see that header name and value. It contains no secrets.
5. **Request bodies are buffered** (up to `maxRequestBodyBytes`, 20 MiB by default) before forwarding.
6. **Upstream response headers are forwarded** (minus hop-by-hop, HSTS, Alt-Svc and `x-tokenfault-*`), including
   `set-cookie`. They are not captured.
7. **Dependencies.** Runtime dependencies are `fastify` and `zod` (plus React in the Studio bundle). CI runs
   `pnpm audit --prod` on every push; it reports known advisories only.
8. **Windows file permissions.** Recording files and directories are not restricted to the current user on
   Windows (POSIX modes are ignored); keep `--record-dir` inside your user profile.
9. **No external audit or fuzzing campaign** beyond the property-style partition and random-chunking tests.
